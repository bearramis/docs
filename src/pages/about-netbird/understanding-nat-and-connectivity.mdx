# Понимание NAT и сетевой связности

## Что такое NAT?

Network Address Translation (NAT) — технология, используемая маршрутизаторами и брандмауэрами, позволяющая нескольким устройствам в частной сети использовать один публичный IP-адрес при доступе в интернет. У устройства есть приватный IP-адрес (например, `192.168.1.50`), но при подключении к сайту маршрутизатор преобразует его в свой публичный IP-адрес и отслеживает, какое внутреннее устройство отправило запрос.

NAT изначально был разработан для экономии IPv4-адресов, но создаёт проблему для peer-to-peer соединений: устройства за NAT не могут напрямую принимать входящие соединения из интернета, поскольку внешнему трафику неизвестно, к какому внутреннему устройству обращаться.

## NAT в разных окружениях

Не все виды NAT работают одинаково. Тип NAT может влиять на то, сможет ли NetBird установить прямое peer-to-peer соединение или потребуется перейти на relay-серверы.

### Простой NAT

Большинство домашних маршрутизаторов используют **Endpoint-Independent Mapping (EIM)**, или «простой NAT». Когда устройство отправляет пакет на любой внешний адрес, маршрутизатор назначает публичную пару IP:port, которая остаётся неизменной независимо от назначения.

**Как это работает:**
1. Устройство `192.168.1.50:12345` отправляет UDP-пакет на сервер A
2. Маршрутизатор преобразует его в `203.0.113.10:54321`
3. Когда устройство отправляет другой пакет на сервер B, маршрутизатор использует ту же публичную привязку `203.0.113.10:54321`
4. Любой сервер, знающий эту привязку, может отправить пакет обратно устройству

**Почему P2P обычно работает:** поскольку привязка постоянна, STUN-сервер может определить публичный IP:port, передать его peer, а peer сможет отправить пакеты напрямую. Маршрутизатор пропустит ответный трафик, поскольку он соответствует существующей привязке.

```
┌─────────────────┐     ┌──────────────┐     ┌─────────────────┐
│  Ваше устройство│────▶│ Домашний     │────▶│    Интернет     │
│ 192.168.1.50    │     │ маршрутизатор│     │                 │
│    :12345       │     │  (Easy NAT)  │     │                 │
│                 │     │ 203.0.113.10 │     │                 │
└─────────────────┘     │    :54321    │     └─────────────────┘
                        └──────────────┘
                              │
                    Один порт для всех назначений
```

### Ограничительный NAT

Многие корпоративные брандмауэры и некоторые маршрутизаторы уровня ISP используют **Endpoint-Dependent Mapping (EDM)**, или «симметричный NAT». Здесь публичная привязка IP:port меняется в зависимости от назначения.

**Как это работает:**
1. Устройство `10.0.5.100:12345` отправляет UDP-пакет на сервер A
2. Брандмауэр преобразует его в `198.51.100.5:60001`
3. Когда устройство отправляет пакет на сервер B, брандмауэр назначает другую привязку `198.51.100.5:60002`
4. Пакеты от сервера B не могут использовать привязку сервера A

**Почему P2P сложнее:** когда STUN-сервер определяет ваш публичный IP:port, эта привязка действительна только для трафика к самому STUN-серверу. Когда peer пытается отправить пакеты на этот адрес, брандмауэр может отклонить их или создать другую привязку.

```
┌─────────────────┐     ┌──────────────────┐     ┌─────────────────┐
│  Ваше устройство│────▶│ Корпоративный    │────▶│    Интернет     │
│  10.0.5.100     │     │ брандмауэр       │     │                 │
│    :12345       │     │ (Symmetric NAT)  │     │                 │
└─────────────────┘     │ 198.51.100.5     │     └─────────────────┘
                        │ :60001 → Сервер A│
                        │ :60002 → Сервер B│ Другой порт для каждого назначения
                        └──────────────────┘
```

**Дополнительные ограничения:** ограничительные NAT-брандмауэры часто:
- полностью блокируют UDP или ограничивают его определёнными портами;
- требуют пропускать трафик через HTTP/HTTPS-прокси;
- выполняют глубокий анализ пакетов, мешающий работе протоколов туннелирования;
- имеют строгие правила исходящего трафика, разрешающие подключения только к известным назначениям.

### Carrier-Grade NAT

Мобильные операторы обычно используют **Carrier-Grade NAT (CGNAT)**, добавляя дополнительный уровень NAT между вами и интернетом. Телефон находится за NAT во внутренней сети оператора, а эта сеть, в свою очередь, находится за ещё одним NAT, обращённым в интернет.

**Проблема двойного NAT:**
```
┌─────────────┐     ┌───────────────┐     ┌───────────────┐     ┌──────────┐
│  Телефон    │────▶│  Базовая      │────▶│  Carrier NAT  │────▶│ Интернет │
│ 10.x.x.x    │     │  станция      │     │   (NAT 2)     │     │          │
└─────────────┘     │   (NAT 1)     │     └───────────────┘     └──────────┘
                    └───────────────┘           │
                           │                    │
                    Приватный IP          Публичный IP
                    100.64.x.x             (общий для многих пользователей)
```

**Проблемы для P2P:**
- необходимо пройти через два уровня NAT;
- операторы часто используют симметричный NAT на уровне CGNAT;
- публичные IP-адреса разделяются тысячами пользователей;
- у привязок могут быть короткие тайм-ауты (30–60 секунд);
- сетевые условия часто меняются при перемещении между базовыми станциями.

<Note>
Диапазон `100.64.0.0/10`, который встречается в мобильных сетях, зарезервирован для Carrier-Grade NAT. NetBird также использует этот диапазон для внутренней адресации — это сделано намеренно, чтобы избежать конфликтов с типичными приватными диапазонами.
</Note>

### NAT 1:1

Облачные виртуальные машины и серверы в дата-центрах представляют другой сценарий.

**Публичное облако (AWS, GCP, Azure):**
- виртуальные машины часто имеют приватные IP с NAT 1:1 на публичный IP (Elastic IP и т. п.);
- для исходящих соединений это ведёт себя как простой NAT;
- группы безопасности управляют входящим доступом, но не влияют на поведение NAT;
- P2P обычно работает хорошо и, как правило, не требует изменения правил брандмауэра.

**Приватные/on-premises дата-центры:**
- NAT может отсутствовать (плоская сеть с публичными или маршрутизируемыми IP);
- либо сеть может находиться за корпоративными брандмауэрами с ограничительным NAT;
- часто действуют строгие правила исходящего трафика.

## NetBird Relay

Когда прямые peer-to-peer соединения невозможны (обычно из-за особенностей NAT), NetBird использует relay-серверы для обеспечения связности. NetBird включает собственную систему relay, оптимизированную для этого сценария.

### Как работает Relay

NetBird relay — лёгкий сервер, который пересылает зашифрованный трафик WireGuard между peers, когда они не могут соединиться напрямую. В отличие от традиционных TURN-серверов, relay NetBird использует собственный протокол, разработанный для эффективной передачи данных.

**Транспортные протоколы:**
- **QUIC** — современный протокол на базе UDP со встроенным шифрованием. Это основной транспорт с меньшей задержкой.
- **WebSocket** — протокол на базе HTTP, работающий поверх TCP. Он используется как резервный вариант, когда UDP заблокирован, поскольку для брандмауэров выглядит как обычный HTTPS-трафик.

При подключении клиента к relay-серверу оба протокола запускаются одновременно, и используется тот, который успешно подключится первым. Если QUIC (UDP) не работает из-за сетевых ограничений, WebSocket (TCP) автоматически становится резервным вариантом.

### Выбор Relay

Когда два peer должны обмениваться данными через relay:

1. Оба peer получают сведения о relay-серверах от NetBird Management Service
2. Signal помогает peers согласовать relay-сервер
3. Оба peer подключаются к выбранному relay-серверу
4. Трафик проходит через relay, оставаясь зашифрованным end-to-end

NetBird поддерживает несколько экземпляров relay-серверов для высокой доступности. Если relay-сервер становится недоступен, peers могут переключиться на другой.

<Note>
В self-hosted развёртываниях можно запускать собственные relay-серверы. Для лучшей производительности размещайте relay-серверы географически близко к пользователям.
</Note>

## P2P и ретранслируемые соединения

### P2P (Peer-to-Peer) соединения

Когда NetBird устанавливает P2P-соединение, трафик идёт напрямую между peers без промежуточных серверов:

```
┌──────────────┐                                    ┌──────────────┐
│    Peer A    │◀──────── Зашифрованный WireGuard ─▶│    Peer B    │
│  (Ваш ПК)    │               туннель               │  (Сервер)   │
└──────────────┘                                    └──────────────┘
```

**Преимущества:**
- **Меньшая задержка:** пакеты проходят по кратчайшему сетевому пути;
- **Более высокая пропускная способность:** отсутствует ограничение relay-сервера;
- **Лучшая надёжность:** меньше потенциальных точек отказа;
- **Приватность:** трафик не проходит через стороннюю инфраструктуру.

**Требования:**
- хотя бы один peer должен иметь «дружественный» NAT или публичный IP;
- промежуточные брандмауэры должны разрешать UDP;
- привязки NAT должны оставаться стабильными достаточно долго для hole punching.

### Ретранслируемые соединения

Когда P2P не удаётся установить, NetBird переходит на relay-серверы. Трафик шифруется до выхода с устройства и остаётся зашифрованным во время прохождения через relay:

```
┌──────────────┐         ┌───────────────┐         ┌──────────────┐
│    Peer A    │◀───────▶│ Relay Server  │◀───────▶│    Peer B    │
│  (Ваш ПК)    │         │  (NetBird)    │         │  (Сервер)   │
└──────────────┘         └───────────────┘         └──────────────┘
                                │
                 Трафик по-прежнему зашифрован
                 WireGuard end-to-end
```

**Когда используются ретранслируемые соединения:**
- оба peers находятся за симметричным NAT;
- UDP заблокирован, но разрешён WebSocket через TCP;
- используются агрессивные брандмауэры с глубоким анализом пакетов;
- сеть организации имеет очень строгие ограничения.

**Компромиссы:**
- **Большая задержка:** трафик должен пройти до relay-сервера и обратно;
- **Меньшая пропускная способность:** пропускная способность relay-сервера разделяется между пользователями;
- **Зависимость от географии:** задержка зависит от расположения relay-сервера.

<Note>
Даже при использовании relay трафик остаётся зашифрован end-to-end с помощью WireGuard. Relay-сервер не может расшифровать или просмотреть трафик — он только пересылает зашифрованные пакеты между peers.
</Note>

Чтобы проверить тип соединения на своих машинах и пошагово диагностировать ретранслируемое соединение, см. [Диагностику ретранслируемых соединений](/help/troubleshooting-relayed-connections).

## Как NetBird устанавливает соединения

NetBird использует протокол ICE (Interactive Connectivity Establishment), чтобы найти лучший возможный путь соединения между двумя peers. Это та же технология, которая используется в видеозвонках WebRTC.

### Процесс установления соединения

Когда два peer NetBird должны соединиться:

**1. Сбор кандидатов**

Каждый peer определяет все возможные способы, которыми к нему можно подключиться:

- **Host candidates:** локальные IP-адреса машины (например, `192.168.1.50:51820`). Они собираются путём перечисления всех сетевых интерфейсов устройства.
- **Server reflexive candidates:** публичные IP:port, видимые снаружи NAT (например, `203.0.113.10:54321`). Они определяются отправкой STUN binding request на STUN-сервер, который возвращает наблюдаемые им публичные IP и порт.
- **Relay candidates:** адреса, выделенные TURN/relay-серверами (резервный вариант). Они получаются запросом allocation к TURN-серверу, который резервирует порт на relay и может пересылать через него трафик к peer.

**2. Обмен кандидатами**

Peers обмениваются найденными кандидатами через NetBird Signal Service. Этот обмен зашифрован end-to-end, поэтому Signal Service не может видеть фактическую информацию о кандидатах.

**3. Проверка связности**

Оба peer одновременно пытаются связаться друг с другом, используя все пары кандидатов. ICE выполняет проверки в порядке приоритета, предпочитая прямые соединения ретранслируемым:

```
Приоритет 1: Host ↔ Host                 (прямое соединение в LAN)
Приоритет 2: Host ↔ Server Reflexive     (прямое соединение через NAT)
Приоритет 3: Server Reflexive ↔ Server Reflexive (оба за NAT)
Приоритет 4: Relay ↔ Any                 (резерв через relay-сервер)
```

**4. Установление соединения**

Первая пара кандидатов, успешно обменявшаяся пакетами, становится активным соединением. Затем NetBird настраивает WireGuard для использования этого пути передачи зашифрованного трафика туннеля.

### UDP hole punching

Когда оба peer находятся за NAT, NetBird использует технику **UDP hole punching**:

1. Peer A отправляет UDP-пакет на публичный адрес Peer B (пакет может быть отброшен, но открывает отверстие в NAT для A)
2. Peer B одновременно отправляет UDP-пакет на публичный адрес Peer A (открывая отверстие в NAT для B)
3. Поскольку оба NAT теперь имеют исходящие привязки, ответные пакеты проходят через них
4. Соединение устанавливается через оба NAT-отверстия

```
    Peer A                                           Peer B
      │                                                │
      │──────── UDP to B's public addr ───────────────▶│ (может быть отброшен)
      │                                                │
      │◀─────── UDP to A's public addr ────────────────│ (может быть отброшен)
      │                                                │
      │         Оба NAT теперь пропускают ответный трафик
      │                                                │
      │◀───────────── P2P Connection ─────────────────▶│
```

**Когда hole punching не работает:**
- симметричный NAT на одной из сторон меняет сопоставления портов, нарушая координацию;
- брандмауэры со строгой фильтрацией отбрасывают неожиданный UDP-трафик;
- срок действия NAT-привязок истекает до установления соединения.

Если hole punching не работает в вашей сети, практические способы решения и случаи, когда relay является ожидаемым результатом, описаны в [Диагностике ретранслируемых соединений](/help/troubleshooting-relayed-connections).

## Relay-инфраструктура NetBird

NetBird предоставляет глобально распределённые relay-серверы, чтобы минимизировать влияние на производительность и обеспечивать связность даже в наиболее ограниченных сетях. Система relay поддерживает два транспортных протокола:

- **QUIC:** высокопроизводительный транспорт на базе UDP (основной);
- **WebSocket:** транспорт на базе TCP через порт 443 (резервный при блокировке UDP).

WebSocket особенно важен для корпоративных сетей, разрешающих только HTTPS-трафик, поскольку для брандмауэров он выглядит как обычный веб-трафик.

Для совместимости со старыми клиентами NetBird также поддерживает TURN (Coturn), хотя для новых развёртываний рекомендуется использовать встроенный relay.

## Кратко

| Тип NAT | Типичная среда | Вероятность P2P | Примечания |
|-------------|-------------|----------------|-------|
| Простой | Домашняя сеть | Высокая | Обычно работает без настройки |
| Ограничительный | Офис | Средняя-низкая | Может потребоваться разрешить конечные точки |
| Carrier Grade (двойной) | Мобильные сети | Низкая-средняя | Зависит от оператора; Wi-Fi часто лучше |
| 1:1 NAT | Облачная VM | Высокая | Проверьте правила UDP группы безопасности |

NetBird рассчитан на работу во всех этих окружениях. Когда P2P невозможно, резервный relay помогает сохранить соединение. Тип соединения влияет на задержку и пропускную способность, но уровень безопасности остаётся тем же: трафик всегда шифруется end-to-end с помощью WireGuard.
